# GPU 正确性与性能验证报告

本报告保留首次 GPU 命令行版本的验收证据。后续新增 CPU/GPU 统一工作台，其功能、界面及完整收敛验收另见 `README_WORKBENCH.md`、`validation/dashboard_tests.log`、`validation/dashboard_ui.json` 和 `validation/dashboard_delivery.json`；不以新增界面的结果改写下述原始测速。

日期：2026-09-29，Asia/Shanghai。代码位置为本报告所在目录。结论以对应 JSON 验证记录及其源码哈希为准。

## 1. 对照方法

从原 `BGK_NEE_Windows_20260928_191621/simulation` 按 `plan.json` 复制 18 个冻结文件，逐一检查 SHA-256。CPU 参照直接调用这份冻结求解器，不另写简化的 CPU 算法。历史 `N64, Re100` 结果另作交叉核验。

先完成 CuPy 数组版，运行完整验证并通过，然后实现融合 CUDA 内核并重复相同验证。两者均使用 float64。预先设定场量绝对容差：短轨迹 `2e-12`、全程低 Re `5e-11`；残差容差 `atol=5e-12, rtol=5e-8`。零误差是本机本次观测结果，不承诺任意驱动、版本或硬件都逐位相同。

## 2. 正确性结果

| 场景 | 检查范围 | 数组版 / 融合版结果 |
|---|---|---|
| `16 x 16, Re100` | 第 1、2、12、20、100、300、500、501、1000 步 | 全部通过，场量最大绝对差为 0 |
| `17 x 19, Re100` | 随机密度、速度及非平衡分布扰动，前 20 步 | 全部通过，场量最大绝对差为 0 |
| `256 x 256, Re5468` | 前 1000 步，含启动前后检查点 | 全部通过，场量最大绝对差为 0 |
| `64 x 64, Re100` | 从初态到完整收敛，多个检查点及最终场 | 均在 16148 步收敛，场量最大绝对差为 0 |
| 历史低 Re 交叉核验 | 新跑 CPU 最终场与冻结历史 NPZ | `rho / ux / uy` 差为 0 |

比较对象包含全部节点的九个分布函数和 `rho / ux / uy`，包括壁面与角点；另显式检查壁面速度、步数、停止原因和故障原因。

融合版低 Re 最终诊断：

|---|---:|---:|

| 输出残差，沿用冻结 CPU 诊断 | `9.998477937549365e-7` | `9.998477937549365e-7` |
| GPU 内核用于每步判定的残差 | 不适用 | `9.998477937549363e-7` |

融合版所有已检查对照点中的最大残差绝对差为 `2.08166817117217e-17`；差异来源于并行求和次序，本次没有改变收敛判断。接近阈值的其他轨迹仍可能因浮点舍入而相差一步，不能外推为任意案例停止步数均相同。

质量漂移约 **0.3105%**，是冻结 NEE 模型本身在此案例中的结果，GPU 没有添加质量修正来消除它。当前策略按速度残差收敛、质量单独报告。

每个后端的八项保护与停止规则测试均通过：初态非有限分布、非正密度、超 Ma；实际更新后超 Ma；最少步数、启动完成及连续达标次数；严格质量策略阻止收敛；步数预算和报告时序；不支持的体力配置拒绝。

证据：`validation/correctness_array.json`、`validation/correctness_fused.json`，以及对应日志和低 Re 对照 NPZ。

## 3. 优化内容

1. 数组版保留原操作结构，作为独立、易检查的 GPU 参照。
2. 融合版将流向拉取、BGK 碰撞、内部宏观量计算合并；壁面重构单独执行，保证角点供体均来自本步内部节点。
3. 采用双缓冲减少中间数组分配；诊断采用两级双精度归约，每步只回传六个诊断量。
4. 每步异常检查和收敛判断保留；每 200 步仍执行原报告逻辑和场量回传。未用降低精度、减少诊断频率或改变阈值换取速度。

## 4. 三轮同条件测速

设备：RTX 4060 Laptop GPU 8 GB，驱动 616.56。案例：`N=256, Re=5468, U=0.04, float64`，启动 500 步，最少 2000 步，原每步残差规则。各实现每轮从同一初态开始，预热 100 步后计时 500 步，共三轮；轮换测量顺序。全部重复的最终场与 CPU 第一轮相同，最大绝对差为 0。

| 实现 | 中位数 ms/步 | 三轮范围 ms/步 | 相对 CPU 加速 |
|---|---:|---:|---:|
| 冻结 NumPy CPU | 34.14695 | 33.66931–39.00719 | 1.00 |
| CuPy 逐数组 | 15.60850 | 15.48615–15.67983 | 2.19 |
| 融合 CUDA | 0.46314 | 0.41594–0.61454 | **73.73** |

融合版相对数组 GPU 加速 **33.70 倍**；按整个网格计约 **141.50 MLUPS**。这些是包含 Python 调度、每步保护与停止判据、同步和周期性报告的墙钟时间，不是只计 CUDA 内核的峰值。

计时不含初始化、首次 JIT 编译及最终压缩导出。记录中的 CUDA event span 也包含主机调度造成的流空闲时间，不能解读为纯内核执行时间。笔记本温度、功耗、其他桌面 GPU 活动和任务规模都会影响结果，不把本次加速比视作固定硬件指标。

原 CPU 正式任务在此次验证和测速前已由仪表盘于 01:52:56 暂停。交付只读审计确认求解器 PID 28804、调度器 PID 48584 均为 stopped；因此本次不能标称为“与原生产 CPU 求解器同时计算”的性能结果。没有为测速修改或恢复该状态。

证据：`validation/performance.json` 和 `validation/performance.log`。

## 5. 命令行及持续运行验收

`verify_delivery.py` 检查了数组版和融合版 `N16, Re100, 301` 步的非整报告间隔结束，以及融合版 `N256, Re5468, 1000` 步；重新打开 NPZ、检查形状、精度、有限性和元数据，宏观场与新跑 CPU 相同。验证门禁能够接受匹配记录、拒绝修改后的 CUDA 文件、拒绝失败记录；非有限诊断写为标准 JSON 的 `null`。

另运行融合版 `N256, Re5468, 20000` 步持续测试。首次测得计算及周期报告用时 **8.7579 秒**，约 **0.4379 ms/步**；含进程启动和结果导出的外部总时长 **10.7040 秒**。所有最终宏观场和分布有限，负分布数量为 0，最大 Ma 为 `0.0692820323`。

其最终残差为 `1.0869296520309564e-4`，质量漂移为 `2.49052516991366e-4`，因此正确标记为 **max_iter，未收敛**。该 20000 步测试是持续运行和输出完整性检查，没有进行 20000 步 CPU 逐场对照；高 Re 已直接对照的范围仍为前 1000 步。重复执行交付检查会产生新的结果目录并刷新 `delivery_checks.json`，首次持续测试保留在 `results/cuda-fused_N256_Re5468_20260929_022359_035221`。

标准 JSON 清洗补充后重新完成了整套命令行验收。第二次 20000 步计算及周期报告用时 **9.2709 秒**，外部总时长 **11.6261 秒**，最终诊断与首次相同；结果位于 `results/cuda-fused_N256_Re5468_20260929_022815_600223`。这两次持续运行观测约为 `0.438–0.464 ms/步`，与三轮短程测速量级一致。

依赖 `pip check` 和 Python 字节码编译检查通过。原目录和独立参照中的 18 个冻结文件哈希仍匹配；原 CPU 任务保持暂停。所有本次启动的验证、测速和短算例均正常结束，没有自动留下 GPU 百万步长任务。

证据：`validation/delivery_checks.json`、`validation/delivery_checks.log` 及其引用的 `results/` 目录。

## 6. 结论边界

已验证的是指定冻结模型在上述案例、时长和本机环境内的 GPU 移植等价性，以及可重复的速度改善。未验证高 Re 完整搜索结论、全参数空间稳定性、网格收敛性或原 NEE 模型的物理精度；未引入另一套碰撞模型、边界条件、质量修正或更宽松的停止判据。GPU 主程序目前是独立单算例入口，未连接 CPU 仪表盘、搜索队列或断点续算流程。
